## Accepted in implementation rounds 1–9

- Native GPUI communicates with the background controller module through **HTTP commands and SSE updates**, on localhost. The proposed messages, authentication, and reconnect contract are in the build plan for approval.
- Coding/test execution uses a **restricted container**, not unrestricted commands on the Mac. No home-directory, controller-credential, or Docker-socket access for generated commands.
- The demonstration keeps small TypeScript logic defects triggered through React, with **Node's built-in test runner** and negative controls. **One real-browser smoke scenario is also required before automatic PR publication**, using headless Chromium in the remediation container.
- Intake uses **polling plus a manual Check now action**; 60 seconds is the proposed initial polling default. Repeated observations must not produce competing work for the same issue.
- The prototype runs **one agent/session at a time** for validation and learning, but the implementation must not hardcode one global current issue or conversation.
- Future support must allow independent remediation sessions for **different issues** to execute concurrently, with the operator able to observe all sessions. This does not request a swarm of specialist agents working on one issue.
- Phase control is **hybrid**: the agent chooses investigative/testing activities and requests completion with an assessment; the controller requires recorded green checks for the **same candidate revision**, plus evidence for claimed browser verification. Stale evidence after a code change cannot satisfy the gate. The proposed tool/receipt and failure contracts are in the build plan for approval.
- Persistence uses **one controller-owned SQLite catalogue plus one Pi Durable SQLite file/harness per remediation session**. The catalogue holds atomic admission/ownership, compact history, and PR tracking; each native case file holds its conversation/task/application state. This replaces the earlier single-file decision because detailed data must actually expire; see [ADR 0004](adr/0004-catalogue-and-session-stores.md). One controller owns all stores; this is not one controller process per case.
- GitHub uses a **fine-grained personal access token restricted to the test repository**, not a GitHub App for the initial pilot. No token has been requested, inspected, or provisioned.
- After an initial validation failure, allow at most **two automatic repair/test cycles**, then park the session for **Needs attention**, preserving context/workspace/issue ownership and releasing execution capacity. No failed-check PR is automatically published.
- PR creation ends agent execution, **not issue ownership**: keep the case in progress/Awaiting merge and track PR status without another agent. Use lightweight controller polling, not a webhook or a waiting model.
- After confirmed merge, automatic renewed work requires a **qualifying recurrence from a known fix-containing version**; older/unknown versions cannot trigger another session. A legitimate recurrence starts a fresh session/conversation/branch/worktree linked to earlier attempts.
- A PR **closed without merging** parks the existing case for **Needs attention** rather than automatically publishing a replacement. An unavailable/stale GitHub status retains ownership and is never interpreted as merged.
- The **Needs attention** marker and stopped-work queue are local to GPUI. Accepted actions are Retry from Needs attention with a fresh bounded allowance, Continue after manual pause with remaining limits, Dismiss locally, and Open in Sentry; neither the marker nor dismissal automatically resolves or reprioritizes the Sentry issue.
- New sessions must receive **remediation history**, including what was previously attempted and its outcomes—not only the last published fix. Details are below.
- A **No fix needed** verdict for expected/transient/non-code issues is local, records a reason, and suppresses automatic repeated investigation until explicit operator requeue. Keep observing reports without resolving the Sentry issue. A suspected defect that cannot be reproduced instead needs operator attention.
- Start the controller **explicitly in a terminal**; GPUI connects separately. Closing GPUI leaves it running, but stopping the controller or rebooting does not install/start a replacement or login item.
- Require **base-fails/candidate-passes regression evidence** for the targeted demo scenario and a frozen candidate Git checkpoint, in addition to green existing tests/build checks and the required real-browser scenario. Baseline normal-path tests should start green; a different intentional demo defect must not block every unrelated fix.
- Coding/test/browser execution is **offline after controlled dependency preparation**, with the app and Chromium sharing container loopback. The controller retains its required integration access. No autonomous new dependency installs. **Future requirement:** allow internet research during coding for documentation/error codes; its access mechanism and privacy controls are deferred, not enabled now.
- The execution ceiling is **10 minutes of active work**, replacing the previous turn-count-or-time proposal. Queued, paused, and awaiting-merge time is excluded. On exhaustion, start no new agent actions and park at a safe action boundary for Needs attention; bound individual operations so a hung action cannot wait indefinitely. The two-repair-cycle ceiling also remains. No independent model-turn ceiling was selected.
- Chat while paused/Needs attention/Awaiting merge/finished is **operator notes only**, with no AI reply or silent model wakeup. Active-session messages may steer at a safe boundary; explicit Pause/Resume commands govern execution authority.
- The user wants to **learn 1Password vaults and secrets**, confirmed an existing company account with vault-creation rights, and selected it provided a new vault is not automatically exposed to all colleagues. No new subscription is needed. **Selected scope:** static GitHub/Sentry tokens in 1Password; Pi's refreshable OpenAI OAuth state in a private application-owned local store, not the company vault. **Privacy requirement:** do not create a vault that is unexpectedly exposed to colleagues, add people/groups, or publish share links. Account type and inherited permissions must be settled before creation; credential scope and authorization mode remain open. No vault or item has been created.
- The local GPUI connection uses a **per-controller-run access token** in an application-private 0600 bootstrap file, rotated on restart, with the interface bound to loopback. Service credentials do not enter GPUI; this does not select OAuth credential storage.
- After explicit controller restart and successful credential/reconciliation checks, **automatically recover previously unpaused work** within its preserved budget. Paused/Needs attention work stays paused, local No fix needed/dismissed outcomes stay suppressed, and PR-waiting work remains passive. Restart does not grant another 10 minutes or permit replay of an uncertain publication.
- Remove the disposable workspace **after confirmed PR creation and successful archival**; retain checkpoints, branch references, PR tracking, history, and evidence. Paused/failed/Needs attention work is not discarded; a previously cleaned workspace is reconstructed on an explicit retry.
- Detailed conversations, logs, screenshots, and traces expire **30 days after a terminal local outcome** (merged, No fix needed, or dismissed), with an **explicit cleanup option**. Unfinished cases remain protected. Keep compact prior-attempt summaries, PR/revision links, and duplicate-work guards longer; mark expired original evidence unavailable.

## Testing: distinguish observation from judgment

The controller cannot generally certify that an agent explored the UI sufficiently. It can, however, record whether a controlled browser action actually ran and check a stated expectation—for example, clicking a button and observing expected text. Playwright supports action traces, screenshots/DOM snapshots, and browser assertions. Those are execution evidence, not proof of complete coverage. [E1, E2]

**Accepted:** an agent testing assessment plus recorded green automated checks for a frozen candidate Git checkpoint, including the required real-browser smoke scenario. The targeted regression must also fail on the base revision for the reported reason and pass on the candidate; a dependency/startup failure is not reproduction evidence. If a suspected defect cannot be reproduced, park it for attention instead of inventing a verified fix. Evidence for claimed browser verification must come from performed actions/checks, not merely the model's report. A code change invalidates earlier revision-specific results. Do not accept a model-written “tests passed” statement as a test-run result, or a screenshot alone as proof of correct behavior.

The same distinction applies outside testing: code can check that a Sentry update happened and met permitted fields, not that every semantic triage judgment is correct. The model supplies reasoning; the controller enforces permissions and records observed outcomes.

**Chosen:** headless Chromium in the session container and a maximum of two automatic repair/test cycles after initial validation failure. Exhaustion parks the issue for later operator attention rather than leaving an agent executing or blocking the execution slot. The proposed evidence contract is in the build plan; stopped-queue actions are accepted below. The demonstration defects remain simple logic cases.

A metadata-only check found **Google Chrome 155.0.8059.85** on the Mac. No browser was launched. No global Playwright package was found in the checked installation locations; this is not an installed browser-testing integration. The initial automated browser will instead be containerized Chromium; no host-browser exception or browser integration has been installed.

## Parallel sessions and isolated work

Docker is not limited to one container. A runtime can run multiple containers, subject to the machine's resources; this capability does not prove that this Mac can sustain any particular concurrency. [E4]

Git worktrees allow different branches to be checked out concurrently. They have independent working files but share repository metadata/configuration, so they are not a security sandbox. In particular, do not mount a complete shared repository into every execution environment merely to make linked worktree metadata accessible. [E3]

**Accepted workspace model:**

- One session-specific branch/worktree for each issue's work.
- One restricted execution container per running session; for the prototype the execution concurrency limit is **1**.
- Test the **candidate worktree/revision**, not by switching a shared checkout to the default branch. The default branch is a baseline, not where unreviewed fixes are installed for testing.
- Keep Git management/publication and credentials in the controller module. Exact access to Git metadata and read-only diff/history tools remains to design.
- Scope mutable files, test processes, preview ports, logs, and artifacts to the session. Do not share a writable `node_modules` tree or a single fixed preview process between concurrent sessions.
- A future concurrency increase must not require replacing a global “current session” design. It still requires resource/isolation/concurrency tests; it is not a claim that changing one number makes parallel operation safe.

The operator application must support a session overview and a selected session's phase, conversation, and results, even while only one session executes. Queued/paused/historical work must not be mistaken for additional running agents. The exact GPUI layout remains open.

## Duplicate work and ownership

**Required:** polling, manual intake, repeated Sentry events, and restart recovery must not admit two competing workers for the same issue. A capacity limit of one by itself is insufficient: it could still admit duplicate queued jobs and process them sequentially.

**Accepted admission model:** one unfinished remediation session owns an issue; intake attaches new observations to it rather than creating another session. New reports must not start another agent while the current work is running or paused. Paused work retains that ownership across restart but releases execution capacity so other issues may run. Do not conflate holding an issue's work with consuming a running-worker slot.

Admission must be atomic/persistent; a read-then-write check across asynchronous calls is not sufficient. The selected layout commits ownership, the case record, and a durable provisioning intent in one catalogue transaction before idempotently initializing the native case file. No model/worker starts before initialization is ready. Recovery completes or parks that same claimed case. This is recoverable provisioning, not atomicity across two databases. Exact records remain to design. Do not add distributed locks, a separate queue product, or multiple controller processes opening the same store.

Published-PR cases continue to own their issue while awaiting merge. New reports enrich that existing case; they do not start another agent. PR tracking is controller bookkeeping, not an executing remediation agent, and must not occupy an execution slot. Existing-PR checks and reconciliation after ambiguous GitHub publication remain necessary; issue ownership does not make external actions exactly-once. Merge/recurrence guards and parked-session operator actions are recorded below. A local No fix needed outcome ends that session's execution, while an issue-level disposition prevents automatic re-admission until explicit operator requeue. Requeue creates a fresh session with the prior assessment available; it does not erase the history or resolve Sentry.

## PR tracking and post-merge reactivation

The user expanded the original stopping point: **agent work still ends at PR creation**, but the controller should keep the issue owned/in progress and observe whether that PR was merged. This does not add CI/review-comment iteration, automatic merging, or automatic deployment.

GitHub's PR resource distinguishes open/closed state from merge information. Polling with the existing PR permission can record merged state without a webhook or model request. **Closed is not necessarily merged.** API/authentication failure must remain unknown/stale, not be treated as merged or permission to admit another worker. Manual marking was offered as a fallback if automatic tracking is infeasible; because the API supports tracking, a manual merge override is not a required initial feature. [E10]

**Accepted activation guard:** merge does not mean the demonstration app has updated. A new agent may start only for a genuinely new report from a known running version that incorporates the merged fix. Older, missing, unknown, or unmappable versions keep a visible waiting condition; arrival time after merge alone is insufficient. Sentry's React SDK supports an event release identifier. Full Sentry repository integration is not required merely to send one. [E11, E12]

The selected version-aware rule replaces the proposed manual “fix is active” acknowledgement; that override is not an initial feature. No automatic pull/reset/deployment of the operator's checkout is authorized. Merge confirmation completes the prior session's Awaiting merge state, while its history and the issue's fix-version admission guard survive. Only an eligible new occurrence can atomically claim a fresh remediation session; clearing the previous owner alone is not permission to start work.

**Proposed mechanical implementation:** tag a clean, immutable demo build with its full Git revision, record the actual merged commit rather than assuming the tested PR head is the merge result, and check ancestry in the controller-owned Git module. A dirty/HMR build must not claim a clean revision that no longer describes its served code. Missing commits, a failed fetch, or ambiguous squash/rebase mapping must not silently pass the guard. Ancestry establishes version lineage, not semantic correctness: a later revert or different defect can still produce a qualifying recurrence. Exact mapping checks remain to validate.

## Parked sessions and stopped-work queue

**Accepted intent:** an exhausted case is paused and marked for attention; a stored conversation is not an executing agent. Preserve phase, candidate/workspace, evidence, assessment, retry history, and issue ownership. Release execution capacity so other issues can run. Repeated reports attach to the stopped case and do not spawn another agent.

**Accepted location:** an application-local Needs attention marker plus a stop reason, shown in a dedicated GPUI filter/queue. Do not add a Sentry marker/status/priority mutation or automatic Resolve operation.

**Accepted operator actions:** Retry the same Needs attention session, with an operator note and a fresh bounded repair budget; Dismiss locally with a reason; Open in Sentry. Retain prior retry counts and evidence in history when granting a fresh budget. Local dismissal preserves an explicit suppression/disposition so the next poll cannot immediately create another agent; renewed work requires an explicit operator action. “Dismiss locally” is not Sentry's Resolve operation. If the user edits the candidate before continuing, old revision-specific validation is stale.

**Selected command distinction:** ordinary Continue after a manual pause preserves the remaining active-work/repair allowance; explicit Retry from Needs attention grants a new bounded allowance with a note. Neither pausing nor restarting resets limits. Earlier usage and attempts remain recorded.

A PR closed without merge enters this queue and retains its session, saved work, and ownership. No replacement PR is created merely because polling notices closure. A manual retry must have explicit operator intent; exact reason-specific resume transitions remain to specify. With the selected post-publication workspace cleanup below, a removed working directory would be reconstructed from the saved checkpoint on that explicit retry, not silently lost.

Worker/browser/container cleanup should free runtime resources without deleting the saved work; do not keep a model call running while waiting for human input. The proposed teardown/recreation and retention contracts are specified in the build plan and require implementation tests.

## Remediation history for renewed investigation

**Required by the user:** when the same issue still occurs after a merged fix, the fresh session must know what was previously attempted. A new conversation must not mean an amnesiac investigation or automatic repetition of the last patch.

Retain earlier investigation/proposal summaries, meaningful candidate changes (including failed repair cycles), observed check results, testing limitations, operator notes/dispositions, PR references, actual merge revisions, and the triggering event/version. Keep facts separate from agent hypotheses and from claims of coverage. Evidence for an earlier tested candidate does not automatically validate a different final merged revision.

**Proposed small interface:** the remediation module supplies a bounded history brief and an index of retained attempts before the first new investigation turn, with read-only access to linked retained diffs, check receipts, and conversations as needed. Expired details must be explicitly identified as unavailable, not represented as still-retained original evidence. Use the existing issue/session records and artifact store; no vector database, extra summarizer agent, or automatic full-transcript replay. Store durable history outside ephemeral execution containers; workspace cleanup must not silently erase the only record of a failed attempt.

The agent compares the current occurrence with prior changes and explains why its new proposal is not merely repeating an ineffective assumption. Sentry grouping does not prove identical root cause, so a prior patch is neither blindly trusted nor categorically forbidden. Context provision is observable; correct use of that context remains an agent judgment subject to new validation.

## Workspace cleanup versus retained history

A **workspace** is the per-session editable checkout where source is changed, commands run, and the preview app is built. Dependencies/build products may also occupy space there. It is neither the operator's original demonstration checkout nor the archive of what the agent did. A runtime container is another separate, disposable execution resource.

**History** records investigation/proposals, attempted changes, operator notes, outcomes, and PR/revision references. **Evidence** records performed tests/browser checks and their logs/screenshots/traces. These must be saved outside the disposable workspace/container. Removing a local Git worktree need not delete its branch, commits, remote PR, or either record type. [E3]

**Selected cleanup point:** after PR creation is confirmed, save the meaningful candidate/attempt checkpoints and patch information plus history/evidence, stop all case execution, then remove the disposable worktree/build cache. Keep the published branch/commit references and PR ownership/tracking; do not delete remote branches or PRs. A closed-without-merge case can rebuild a workspace from the saved checkpoint on manual retry. No fix needed/dismissed terminal cases can similarly clean after archiving any work. Failed/paused/Needs attention work is not automatically discarded merely because its worker stopped.

Cleanup requires successful archival first and must affect only recorded eitri-owned session paths. Never delete the operator's demonstration checkout, another session's working files, 1Password items/vaults, Sentry data, or GitHub objects. Unexpected dirty/unarchived files block automatic removal with a warning; a failed cleanup must not pretend the files were removed, reset ownership, or launch a new agent. Explicit cleanup should distinguish disposable workspace removal from deletion of retained history/evidence and confirm the latter.

**Selected retention scope/clock:** full conversations, detailed logs, screenshots, and browser traces expire 30 days after a terminal local outcome (merged, No fix needed, or dismissed), with an explicit cleanup option. A case merely Awaiting merge is still unfinished; queued/running/paused/Needs attention cases retain recovery data until dealt with. Workspace removal occurs earlier at successful PR handoff without starting a fresh agent or changing that retention clock.

**Selected longer-lived minimum:** retain compact attempt/outcome summaries and PR/commit references so a recurrence after day 30 need not forget all previous work. Full expired evidence is unavailable, not inferred from a summary. Preserve the minimal ownership/disposition/last-merged-version control records needed to prevent duplicate work; ordinary cleanup must not remove those guards and immediately re-admit the issue. This is an explicit exception for compact records, not permission for indefinite hidden full-payload retention. The 30-day policy does not delete source-repository history.

Expiry runs while the controller is running or at its next safe start; this does not install a background cleanup daemon. It applies to eitri's local records, not remote GitHub/Sentry retention or credential expiry. **Implementation gate:** prove actual deletion of whichever persisted payloads the user chooses to expire. Pi's context reset/compaction keeps older entries in storage, and its document-retention setting is an in-memory cache policy, not data expiry. The selected per-session-file layout therefore closes a terminal expired case's readers/harness before removing its native database, SQLite sidecars, and raw artifacts. Verify this with actual cleanup/reopen tests; hiding history in GPUI is not deletion. A cleanup failure must be reported and retried safely rather than declared successful or allowed to delete another case/catalogue/credential file. [E22]

## Persistence re-evaluation after selecting real expiry

The single-file decision predated actual 30-day transcript expiry. A focused check of the pinned public `Storage`/`StorageWrite` interfaces and SQLite implementation found no standard operation to purge a conversation or its immutable transcript entries. Document retirement is not transcript deletion; SQLite inserts entry records, while document-revision deletion serves a different purpose. This does not make a custom maintenance purge impossible, but it is not a supported one-call lifecycle operation we can simply assume. [E23]

**Decision accepted in round 8: B.** The alternatives considered were:

- **A — Keep the single harness/file:** design a version-pinned maintenance purge that safely handles native record references, storage lifecycle, caches, and observers. Do not issue ad-hoc deletes behind a live harness. This preserves native same-commit conversation/state creation but couples retention to more of Pi's storage implementation and needs dedicated correctness tests.
- **B — Catalogue plus one native Pi Durable SQLite file per remediation session:** keep atomic admission/ownership, compact summaries, dispositions, and PR/merge tracking in a small controller-owned catalogue; keep each case's native conversation/task/application state in its own file. After the case is terminal and the expiry deadline passes, close its readers/harness and remove its database and associated raw artifact files without writing a native transcript garbage collector. Global credentials are not case payloads and must not be swept with them. All stores still have one controller owner; no extra server or ORM is required.

**Selected: B**, revisiting the earlier preference because the retention requirement changed the trade-off. Admission atomically claims the issue, creates its catalogue case record, and records a provisioning intent. Initializing the case database is an idempotent next step; no model/worker starts before it is ready. Recovery completes provisioning or parks the same claimed case, never creates another owner because initialization was interrupted. This deliberately trades one cross-cutting native commit for explicit recoverable provisioning and straightforward per-case lifecycle/expiry. [ADR 0004](adr/0004-catalogue-and-session-stores.md) supersedes the earlier choice; application implementation is still not approved.
