## Findings before any live integration

- **Important — canceled stream is not drained OAuth rotation.** `test/helpers/pi-auth.mjs:237–250` explicitly observes caller settlement while refresh is still active, then separately releases and awaits persistence. In contrast, `prototypes/pi-native-stream.mjs:54–56,79–80` kills its helper on cancellation/deadline, and `prototypes/pi-native-child.mjs:49–59` deliberately forbids refresh. The native drainage tests therefore cannot certify safe built-in rotating-token disposal. Reusing that kill policy for a real refreshing store could interrupt persistence after remote rotation; no actual credential-loss incident is claimed. Before live use, select a supported ownership/drainage design and prove it offline at cancellation, deadline, close and parent-crash boundaries. Do not fix this by extracting/copying tokens, patching Pi internals or weakening the allowance contract.
- **Important — shared-store ownership is unresolved.** `test/helpers/pi-auth.mjs:135–185` injects `InMemoryCredentialStore`; `test/pi-native-isolation.test.mjs:56–61` creates only a deletion sentinel. Neither exercises Pi's actual persistent-store locking with an independent Pi process. Before real shared-store access, verify supported serialization/rotation behavior or obtain an explicit operational-exclusion decision for independent clients. A single Eitri execution slot is not cross-process locking. Any exclusion addresses contention, not the separate drainage finding above.
- **Suggestion — retain evidence boundaries.** `test/pi-native-repairs.test.mjs:217` covers one nonzero repair-count crash checkpoint, not a Cartesian product of every repair/auth/crash state. Preserve that label rather than broadening the claim to full compatibility.

These are unresolved pre-live gates, not newly introduced runtime regressions or reasons to discard the bounded offline evidence. No Critical finding is identified within this offline checkpoint.
